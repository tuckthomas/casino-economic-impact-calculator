# Available and selected facility inputs

The workbench lets users choose the physical attributes used for facility attraction and edit their weights. Availability is calculated from the selected sealed datasets, complete study-origin selection, effective date, development program and the same origin-based competitive universe used by execution. Changing those selections refreshes availability; an older asynchronous response cannot replace a newer selection.

A physical input is available only when every facility that needs it has a finite, nonnegative modeled value. A recorded zero is available; null is missing. Structural comparisons use a common complete feature set across the competitive field. Observed-GGR incumbents do not need physical attributes; the proposed facility still does. Hybrid mode conservatively requires physical coverage across its potential fallback field. No competitor is dropped to make an input available.

Unavailable checkboxes and their parameter editors are disabled and explain the missing coverage. Available inputs have explicit checkboxes and weight controls. Selecting a zero-weight input starts it at the disclosed scenario weight of 1; it does not establish a calibrated weight. Inputs made unavailable by a changed selection are deselected with a visible notice. Tourism/traffic parameter editors are also inactive when no corresponding observations are selected.

The API independently rechecks availability. Explicit unknown, duplicate or unavailable feature selections are rejected before draft creation or routing. An omitted selection means the available feature set; an explicit empty selection means neutral physical attraction (mass 1), with a saved warning. Demand, routed travel, outside-option and any observed-revenue attraction calculations still apply. A selected zero-weight term has no effect. Missing values in active terms are rejected rather than replaced with reference attributes. Reference values remain normalizers for actual inputs, not substitutes for missing observations.

`selectedFacilityFeatureKeys` is included in run requests and saved scenario definitions, preserved in sensitivity requests, and frozen in the immutable run manifest alongside `facilityInputPolicy=available-selected-inputs-v1`. HTML/PDF/JSON/CSV report version `professional-v7` includes the stored selection; historical runs without it are labeled as not having recorded that choice. Existing stored artifacts are not rewritten.

New matched-revenue calibration uses the same feature catalog and strict selection policy across its compared physical field. Only explicit historical scope-mismatch diagnostic replay retains the previous reference-imputation equation; it cannot publish accepted defaults or become a current UI selection. Retained historical evidence is unchanged.

Verification covers missing versus zero attributes, refreshed availability, omitted/empty/explicit selections, unknown/duplicate/unavailable selection rejection, exclusion of inactive terms, neutral attraction, matching calculation values, a database-backed origin-field availability endpoint, rendered disabled/enabled UI controls, and saved selection in reports. This feature does not establish empirical forecast accuracy or change the existing acceptance thresholds.
